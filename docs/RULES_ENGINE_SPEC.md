# Спецификация подсистемы правил безопасности (KeenGuard Rules Engine)

Документ определяет архитектуру, модель данных, алгоритмы валидации и пользовательский интерфейс для гибкого движка правил и фильтров сетевой безопасности (**Security Rules & Automation Engine**) в системе KeenGuard.

---

## 1. Концепция и цели

### 1.1. Проблема текущей реализации
Ранее правила обработки сетевого трафика (например, распознавание стримов, контроль SMB/SSH, лимиты объемов в 10 КБ) были жестко зашиты в Python-код (`LanTrafficTracker`, `AuditSession`, `BUILTIN_LAN_PRESETS`). Это создавало три критические проблемы:
1. **Непрозрачность («Черный ящик»):** Пользователь не видел, почему конкретный пакет был пропущен или заблокирован.
2. **Ограниченная гибкость:** Невозможность задать собственные порты для домашних сервисов (Jellyfin, Plex, локальные камеры, кастомные порты умного дома) без правки исходного кода.
3. **Бинарность реакций:** Выбор между полным аппаратным карантином устройства и полным игнорированием без возможности точечной настройки (тихий пропуск, запись PCAP, пуш в Telegram, смена пресета).

### 1.2. Цель Rules Engine
Трансформация KeenGuard в **домашнюю мини-SIEM/IDS систему** с прозрачным цепочечным исполнением правил (First-Match Win), интуитивным визуальным конструктором, защитой от ошибок конфигурации (Rule Linter) и сквозной телеметрией каждого срабатывания.

### 1.3. Принцип технического реализма (L2 vs L3/L4 Enforcement)
* **Аппаратные ограничения L2 (Bridge0):** Устройства внутри одной подсети `192.168.1.0/24` общаются напрямую через кремниевый свитч роутера. Движок правил не может «на лету сбросить одиночный L2-кадр» между двумя клиентами.
* **Реальные механизмы исполнения (Reactive & Hardware):**
  1. *Аппаратный бан WAN:* Блокировка выхода в интернет через Keenetic RCI (`set_device_policy(mac, access="deny")`).
  2. *DNS Sinkhole:* Принудительный возврат `0.0.0.0` на уровне встроенного DNS-сервера роутера.
  3. *Форензика и сбор улик:* Мгновенная запись сырого `.pcap` дампа из кольцевого буфера.
  4. *Динамическая смена пресета:* Перевод устройства на строгий локальный профиль (Local-Only).
  5. *Оповещения:* Адресный пуш в Telegram (с обходом тихого часа или в дайджест).

## 2. Иерархия и порядок применения (Execution Order)

Обработка трафика ведется по классическому принципу межсетевых экранов: **сверху вниз до первого совпадения (First-Match Win)**.

```
┌────────────────────────────────────────────────────────────────────────┐
│  ЗОНА 1: СИСТЕМНОЕ ЯДРО (Core Failsafe, ID 1–10) 🔒                    │
│  • Нельзя удалить, нельзя опустить вниз                                │
│  • Защищает системные службы: DNS (53), DHCP (67/68), Web UI (9989)    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (если не совпало)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  ЗОНА 2: ЕДИНЫЙ ПУЛ ПРАВИЛ (Main Rules Pool, ID 11–998) ↕️             │
│  • Полная свобода Drag & Drop перемещения                              │
│  • Включает базовые шаблоны [Встроенное] и кастомные правила [Кастом]   │
│  • Кастомные разрешающие правила МОГУТ стоять выше встроенных          │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (если не совпало)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  ЗОНА 3: ДЕФОЛТНАЯ ПОЛИТИКА (Default Catch-All, ID 999) 🔒             │
│  • Всегда в самом конце                                                │
│  • Применяет стандартную политику назначенного профиля устройства      │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1. Зона 1: Системное ядро (Core Failsafe, ID 1–10) 🔒
* **Назначение:** Гарантия доступности сети и предотвращение ситуации, когда пользователь случайно отрезает роутер от связи или блокирует интерфейс управления.
* **Фиксация:** Строки заблокированы от редактирования и перетаскивания.
* **Правила ядра:**
  * `#1 [CORE] DHCP Infrastructure`: Разрешен обмен по портам UDP 67/68 между клиентами и роутером.
  * `#2 [CORE] Router DNS Resolver`: Разрешены стандартные запросы UDP/TCP 53 к шлюзу роутера.
  * `#3 [CORE] KeenGuard Management`: Защита порта веб-интерфейса `9989` от блокировки доверенным хостам.

### 2.2. Зона 2: Основной пул (Main Rules Pool, ID 11–998) ↕️
* Базовые системные шаблоны и пользовательские правила сосуществуют в едином списке.
* Пользователь может поднять кастомное разрешающее правило (например, «Разрешить SMB для Backup-ПК») **выше** базового блокирующего правила («Блокировать SMB от всех»).
* Каждое правило имеет статус `Включено / Выключено` без необходимости его удаления.

### 2.3. Зона 3: Замыкающее правило (Catch-All, ID 999) 🔒
* Пакеты, не попавшие ни под одно специфическое правило, обрабатываются стандартным пресетом профиля устройства (`trusted`, `smart_tv`, `camera`, `iot`, `guest`).

## 4. Спецификация блоков условий и реакций

### 4.1. Селектор источника (КТО)
* **Поля выбора:**
  * Устройства по MAC/IP (мультиселект из зарегистрированных в сети хостов).
  * Профили безопасности (`smart_tv`, `camera`, `iot`, `trusted`, `guest`).
  * Сетевые интерфейсы / сегменты (`Home / Bridge0`, `Guest / Bridge1`, VLANs).
  * Вендоры оборудования по OUI (например, `Espressif`, `Tuya`, `Xiaomi`).
  * Флаги свойств (например, `random_mac` — устройства со случайным MAC).
* **Инверсия источника (`invert: true`):**
  * Позволяет сформулировать: *«Все устройства сети, КРОМЕ указанных»*.

### 4.2. Селектор назначения (КУДА И КАК)
* **Направление потока:**
  * `lan_to_lan`: Внутри домашней сети (к ПК, NAS, ТВ).
  * `lan_to_wan`: Исходящий в интернет.
  * `lan_to_router`: К служебным портам роутера (80, 443, 22, 53, 8200).
  * `wan_to_lan`: Входящие соединения (UPnP пробросы).
* **Целевые узлы и порты:**
  * IP-адреса, подсети CIDR (`192.168.1.0/24`).
  * Домены и маски (`*.samsungcloud.com`, `*.ru`).
  * Порты: ручной ввод (`8096`), списки, диапазоны (`50000-50020`) или готовые сервисы из каталога (`Jellyfin`, `Plex`, `RTSP`, `SMB`, `SSH`, `AirPlay`, `Google Cast`).
* **Инверсия портов (`invert_ports: true`):**
  * Позволяет сформулировать: *«Любые порты, КРОМЕ 554 (RTSP)»*.

### 4.3. Поведенческий и временной контекст (КОГДА И СКОЛЬКО)
* **Порог объема:**
  * Оператор: `>` (больше) или `<` (меньше).
  * Значение и размерность: КБ, МБ, ГБ.
  * *Сценарий `< 1 КБ`:* Обнаружение C2-маячков (Heartbeats) ботнетов.
  * *Сценарий `> 10 КБ`:* Выделение непрерывного потокового медиа.
* **Порог скорости передачи:**
  * Оператор: `>` или `<`. Значение: Кбит/с, Мбит/с.
  * *Сценарий `> 1.5 Мбит/с`:* Детектор скрытой трансляции видео с камер наружу.
* **Временное окно:**
  * `always`: Круглосуточно.
  * `night_only`: Только в часы ночной форензики (`00:00–07:00`).
  * `day_only`: В дневные часы.

### 4.4. Действия и реакции (ЧТО ДЕЛАТЬ)
* **Уровень опасности (Severity):** Фиксированная шкала `INFO` (синий), `NOTICE` (зеленый), `WARNING` (желтый), `CRITICAL` (красный).
* **Режим обработки (Action Mode):**
  * `pass` (Белый список / Игнорировать): Легитимный трафик. Не генерирует инцидентов, не шлет алертов.
  * `alert` (Инцидент / Наблюдение): Фиксирует нарушение политики в журнале.
* **Переопределение действий (Action Overrides):**
  * `notify_telegram`: `false` / `true` (с выбором `immediate` — мгновенно с обходом тихого часа, или `digest` — включить в сводку).
  * `record_pcap_seconds`: Запись кольцевого буфера (`15`, `30`, `60`, `120` сек).
  * `hardware_wan_block`: Аппаратное отключение интернета на роутере через Keenetic RCI.
  * `apply_preset_id`: Динамический перевод устройства на кастомный пресет (например, `preset_iot_strict` или `preset_quarantine`).

## 5. Сквозная атрибуция событий к правилам (Rule Attribution)

Для полной наблюдаемости в модель инцидентов `SecurityEvent` и структуру потоков Conntrack добавляются два обязательных поля:
1. `matched_rule_id: Optional[str]` — уникальный строковый идентификатор сработавшего правила.
2. `matched_rule_name: Optional[str]` — понятное человекочитаемое название правила на момент срабатывания.

### Отображение в интерфейсе и Telegram:
* В журнале событий (Logs/Incidents) и в карточке устройства выводится кликабельный бейдж:
  `[#102 Smart TV Media Stream]`.
* При клике на бейдж система открывает вкладку «Правила», прокручивает страницу к строке правила #102, подсвечивает ее синей анимацией и открывает модальное окно редактирования.
* В уведомлении Telegram добавляется строка:
  `Правило: #104 (Block Mirai Telnet/SMB)`.

## 6. Валидатор порядка правил (Rule Linter & Conflict Analyzer)

Валидатор запускается **строго по нажатию кнопки «Сохранить изменения»** (а не при каждом перемещении строки), что гарантирует высокую производительность и отсутствие раздражающих мигающих сообщений.

### 6.1. Классификация ошибок и предупреждений:
1. **Затенение правил (Shadowed Rule / Мертвые правила):**
   * *Условие:* Разрешающее правило стоит **ниже** более широкого блокирующего правила по тому же порту/устройству.
   * *Пример:* Правило #15 «Блокировать порт 445 для всех», а ниже Правило #16 «Разрешить порт 445 для ПК 192.168.1.25».
   * *Статус:* Предупреждение (Warning). Правило #16 никогда не получит пакет.
2. **Нарушение приоритета ядра (Core Priority Breach):**
   * *Условие:* Пользователь пытается переместить кастомное правило в Зону 1 (выше системных правил ядра 1–10).
   * *Статус:* Критическая блокировка (Error). Интерфейс физически запрещает такое перемещение.
3. **Прямой конфликт условий (Direct Rule Conflict):**
   * *Условие:* Два правила имеют 100% идентичные фильтры источника, назначения и портов, но разные действия (`pass` vs `alert`).
   * *Статус:* Предупреждение (Warning). Нижнее правило никогда не исполнится.

### 6.2. Модальное окно подтверждения (Soft Linter Warning):
Если валидатор обнаружил предупреждения при нажатии кнопки «Сохранить», отображается диалог:
```
┌────────────────────────────────────────────────────────┐
│ ⚠️ Обнаружен конфликт порядка правил                  │
│                                                        │
│ • Правило #105 "Разрешить SMB для ПК" полностью        │
│   перекрывается Правилом #102 "Блокировать SMB".       │
│   Оно никогда не сработает при текущем порядке!        │
│                                                        │
│ [ ↩ Вернуться и исправить ] [ ⚠️ Сохранить принудительно ] │
└────────────────────────────────────────────────────────┘
```
Пользователь предупрежден, но решение остается за ним.

## 7. Спецификация пользовательского интерфейса (UI/UX)

### 7.1. Вкладка навигации «Правила» (Rules Engine)
В главное верхнее меню добавляется раздел:
`Дашборд | Устройства | Инциденты | Правила | DNS & Домены | Настройки`.

### 7.2. Таблица правил (Rules Table View)
* Строки таблицы поддерживают **Drag & Drop** (за ручку `⋮⋮`).
* По каждой строке выводятся:
  * Порядковый номер (`#1`, `#2`, `#101`...).
  * Тумблер быстрого включения/отключения (`ON / OFF`).
  * Тип: `[Ядро 🔒]`, `[Базовое]`, `[Кастом]`.
  * Название и краткие чипы условий: `Smart TV ➔ LAN:8096, 32400`.
  * Чип реакции: `[PASS]` (зеленый) или `[CRITICAL Alert]` (красный).
  * **Интерактивный счетчик срабатываний:** кликабельный бейдж `1 840 (85 за 24ч)`.
  * Кнопки действий: `⚙️ Редактировать`, `🗑️ Удалить` (только для кастомных).

### 7.3. Нижняя плашка несохраненных изменений (Draft Bar)
* При перемещении правил или изменении статусов внизу экрана всплывает фиксированная панель:
  `🟡 Изменен порядок 3 правил. [Сбросить] [💾 Сохранить изменения]`.
* **Защита от потери данных (Unsaved Guard):**
  * При попытке клика по другим вкладкам интерфейса или закрытии окна браузера срабатывает перехват: *«У вас есть несохраненные изменения в правилах. Покинуть страницу?»*.

### 7.4. Дриллдаун счетчика срабатываний (Hit Telemetry Drawer)
При клике на бейдж счетчика срабатываний выезжает боковая панель с детальной телеметрией:
* Общее число совпадений с момента создания правила.
* Срезы за последние 24 часа.
* Список последних 10 конкретных сессий с точными таймстемпами, IP источника, IP назначения, портом, протоколом и переданным объемом байт.
* Кнопка: `[🔍 Показать все события этого правила в журнале инцидентов]`.

### 7.5. Симулятор пакетов (Dry-Run Traffic Tester)
В верхней панели инструментов таблицы доступна кнопка **«🧪 Протестировать трафик»**:
* Пользователь указывает тестовые параметры: `Src IP`, `Dst IP`, `Port`, `Protocol`, `Volume`.
* Система прогоняет виртуальный пакет по цепочке правил и подсвечивает зелёной рамкой конкретную строку таблицы, которая первой перехватит этот пакет, с выводом итогового вердикта (`PASS` или `ALERT`).

## 8. Архитектурный план реализации (Roadmap)

1. **Модели и БД (`keenguard/db/`):**
   * Создание таблицы `security_rules` и репозитория `rules.py`.
   * Миграция стандартных встроенных шаблонов (`Core` + `Built-in`).
   * Добавление `matched_rule_id` в `security_events`.
2. **Ядро проверки правил (`keenguard/core/rules/`):**
   * Модуль `matcher.py`: высокопроизводительное сопоставление сетевых пакетов/сессий Conntrack с кэшированными хэш-таблицами правил (O(1)).
   * Модуль `linter.py`: алгоритм выявления затенения (shadowing) и конфликтов.
   * Интеграция в `LanTrafficTracker` и `AuditSession`.
3. **API эндпоинты (`keenguard/web/routes/rules.py`):**
   * `GET /api/rules` — получение полного упорядоченного списка правил.
   * `POST /api/rules` — создание пользовательского правила.
   * `PUT /api/rules/{id}` — обновление параметров правила.
   * `PUT /api/rules/reorder` — пакетное сохранение нового порядка правил с валидацией.
   * `DELETE /api/rules/{id}` — удаление кастомного правила.
   * `POST /api/rules/test` — запуск симулятора трафика (dry-run).
   * `GET /api/rules/{id}/hits` — дриллдаун последних срабатываний.
4. **Пользовательский интерфейс (`index.html`, `app.js`, `style.css`):**
   * Верстка вкладки «Правила & Фильтры».
   * Реализация Drag & Drop сортировки с сохранением состояния.
   * Модальное окно визуального конструктора правил.
   * Всплывающий Drawer телеметрии срабатываний.
   * Интеграция предупреждений валидатора.
